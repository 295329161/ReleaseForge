# 证据与交付约定

优先遵循当前项目约定；没有约定时可采用以下结构，不要求机械增加所有文件。

## 验收记录

在 `validation/<version>/` 保存与该版本相关的可交付证据；敏感原图、完整运行日志和备份放项目外私有归档。建议：

- `results.json`：版本、源码/构建标识、验收范围、逐项结果、问题与复测、限制、最终状态、产物哈希。
- `screenshots/` 及索引：稳定的页面/状态文件名、中文说明、原尺寸图片链接。可用项目现有静态画廊；页面截图和验证清单相互对应。
- `screenshots.json`：页面 ID/路由、状态、进入方式、文件路径、采集来源（浏览器/实机帧缓冲/仿真）、对应版本、SHA-256。必要脱敏要说明。
- 主机测试结果、构建摘要和脱敏运行证据：保留实际执行的命令或工具、环境、返回状态及足以支持结论的结果，不复制无关噪声或损坏的串口字节。

每项验证至少回答：测了什么、实际操作是什么、预期和实际结果是否一致、证据在哪里、是否存在未覆盖条件。截图证明可见状态，业务/硬件证据证明功能结果，不能只依靠图片数量判断完成。

状态语义：

- `pass`：实际执行，结果满足写明的判定条件。
- `fail`：已执行且不符合预期；保留失败及修复后复测记录。
- `partial`：只覆盖部分链路，明确已经证明与尚未证明的内容。
- `not_verified`：未执行或环境不足，写明具体缺口。
- `not_applicable` / `not_implemented`：当前产品不适用或明确未实现，不计为功能通过。

报告应区分“验收范围内可发布”与“所有可能场景均已验证”。不能用一个总 `pass` 隐藏部分验证。历史版本证据不被覆盖，当前报告引用其适用范围；新变更的受影响链路另行复测。

## 整理与发布包

保留足以重建、维护、验证、安装和恢复当前版本的文件。不把有效测试、诊断工具、许可证、依赖锁或历史验证证据误删为临时文件。归档清单应能追溯移动来源与去向，未知用途文件不做永久删除。

发布包按产品类型包含所需的运行/固件产物、源码快照或提交标识、必要资源、许可证、安装/升级说明、支持范围、验证记录与 SHA-256 清单。调试符号按项目需求保留，可单独交付。禁止把整个工作目录不加选择地打包，尤其是 NVS/整片 Flash、用户存储、API Key、环境文件、私钥和私有日志。

发布步骤应验证：

1. 版本、提交、依赖锁和实际构建产物一致；构建暂存副本没有漏同步组件清单、资源或锁文件。
2. 使用同一套最终产物安装/烧录或完成项目适用的运行检查；如只有模拟测试，记录该限制。
3. 包内目录结构、安装说明、链接和校验清单可用；压缩包能够读取，校验值与交付文件一致。
4. 旧标签和旧发布包保持原样；新提交没有夹带用户无关改动。
5. 区分候选包、本地正式版本、远程上传和生产部署，只有实际完成相应动作才能报告该状态。

示例调用：“使用 $release-forge 审查当前项目所有功能并保存逐页截图，修复后整理归档，满足发布条件时发布为 2.0.0。”没有明确新版本时，不从这个示例推断版本号。
